## 1. Groups 3 and 95 — RESOLVED, definitions built

Both are one park represented twice, visitor content vs NPS, with no
`state_parks` GIS row to break the tie. I confirmed **no `state_parks`-backed
row matching "Old Town" or "Tubac" exists at all** `[literal]`, so unlike Hat
Rock and Salton Sea there is no missing third member to find. The tie is real.

### ⚠️ The blocker nobody had hit yet

**The executor could not express Adam's decision.** `pickCanonicalGroup` returns
`null` on a tie and `planGroup` hard-stops. Groups 3 and 95 are *definitionally*
tied — that is why #379 listed them — so "pick NPS" had no representation in the
group-file format. `[literal — the first attempt failed with "canonical is
undecidable over the merging members"]`

Fixed with an explicit `canonical_override { mp_id, decided_by, reason }`, which
is the mechanism `merge-canonical.ts` already prescribed in its own docs:
*"Consumers that want an override for undecidable groups MUST apply it
explicitly, not by adding heuristics here."* Guards, each verified to fire:

| Case | Result |
|---|---|
| Override names a non-member | FATAL ✓ |
| Blank `reason` or `decided_by` | FATAL ✓ |
| Override disagrees with `canonical_mp_id` | FATAL ✓ |
| **Override supplied but the rule CAN decide** | FATAL ✓ |
| Tied group with no override | FATAL ✓ |

The fourth is the important one: an override is only honoured on a genuine tie.
Overriding a working rule is how a mis-typed id becomes a wrong merge, and it
would also mask real canonical drift.

### #379's unverified caveat — resolved, favourably

#379 warned that after an NPS-canonical merge the visitor row's **hours** might
be lost, and flagged it explicitly as not verified. It matters because
`resolve_field()` **INNER JOINs** `field_precedence`: a source with no
precedence row for a field is dropped entirely, and `hours` is in
`v_clearable_fields`, so an unresolved value is actively set to NULL.

Two things make it safe, both measured `[literal]`:

- `field_precedence` **has** `hours` rows for `california_state_parks` and
  `arizona_state_parks` (both priority 3). `nps` is priority 2 — *higher* — but
  the NPS source_records for both groups **carry no `hours` in
  `normalized_payload`**, and `resolve_field` skips null values. NPS cannot win
  a field it does not have.
- Verified end-to-end on TEST, not just reasoned: a shape-matched merge produced
  `hours = {"monday":"9-5","tuesday":"9-5"}` with `attribution.hours =
  california_state_parks`, and the NPS description won (precedence 1).

**Caveat worth keeping:** this holds *because* NPS carries no hours today. If a
future NPS ingest starts populating hours, priority 2 beats the visitor sources
and the visitor hours would be replaced.

**Built:** `data/merge-groups/2026-09-04-groups-3-and-95.json`. Groups 3 and 95
were also added to `DEFAULT_BLOCKED_GROUPS`, so every #379 group needs
`--force-blocked` *and* its override.

## 2. Groups 77 and 78 — HOLD. Both canonicals are conflations.

Neither is a landmark-vs-park question. Both canonical rows **fuse two different
real-world units**, and the proof is in `source_record.name` `[literal]`:

| group | canonical mp is named | but it carries this source_record | whose name is |
|---|---|---|---|
| **77** | Mayer State Park | `oregon_state_parks:221` | **"Historic Columbia River Highway - Rowena Crest Overlook"** |
| **78** | Fort Rock State Natural Area | `oregon_state_parks:170` | **"Fort Rock Cave"** |

### Group 77 — Mayer State Park (OR)

`72667f33` carries the Rowena Crest **Overlook** visitor record *and* the Mayer
State Park GIS polygon, under the name "Mayer State Park". Its description is
entirely about Rowena Crest and states outright that the viewpoint *"looks down
on Mayer State Park"* — a different place, 1,518.5 m from the correct Mayer row
`[literal]`. The genuine Mayer record is `21335e18` (`oregon_state_parks:117`,
source_record name "Mayer State Park"), which is the row the group would
**absorb into the conflated one**.

**Recommendation: HOLD, do not merge.** Confidence **high**. This is a
pre-existing entity-resolution defect, not a merge decision — merging would
compound it by folding the correct record into the wrong one. The repair is to
split `oregon_state_parks:221` onto its own Rowena Crest master_place; that is
ER work, out of scope here.

### Group 78 — Fort Rock (OR)

Two separate questions, and they resolve differently.

**The landmark-vs-park question is benign.** The atlas row describes the tuff
ring — *"about 4,460 feet (1,360 m) in diameter"* — and the State Natural Area
polygon measures **1.415 km²** `[literal]`, essentially coextensive with a
1,360 m-diameter ring. Unlike Hat Rock, where a 70-foot rock sits inside a
719-acre recreational park, here the protected area *is* the landform.
`[strong inference]` Same entity.

**But the canonical has the same conflation defect as group 77:** `18fcb124`
carries `oregon_state_parks:170`, whose source_record name is **"Fort Rock
Cave"** — a National Historic Landmark, guided-tour access only, described in
its own text as *"near Fort Rock State Natural Area"*. Its description is
mostly about the cave.

**Recommendation: HOLD, second human read needed.** Confidence **medium-high**
that the conflation is real; **low** on what the right repair is. The cave is
administered by OPRD alongside the SNA, so this may be a defensible
"unit + its cave" grouping rather than a mis-link — which is exactly the kind of
call that should not be made from field data alone.

## 3. What recompute actually produces — measured, not assumed

All four validated on TEST with real `merge_master_place()` calls against
shape-matched fixtures (`data/scripts/verify-merge-field-outcomes.ts`).

### Groups 66 / 70 (Dosewallips, Wenatchee Confluence) — half of #379's expectation holds

| | outcome |
|---|---|
| Description | **Picked up from the absorbed visitor row** ✓ — `state_parks` has no `description` precedence row, so its blank cannot win |
| Name | **Stays the truncated canonical form** — final `canonical_name` was `Dosewallips`, attributed to `state_parks` |

The name result is structural, not incidental: `field_precedence` has
`canonical_name` rows for **only `nps` (1) and `state_parks` (4)** `[literal]`.
No visitor source, `atlas_oddities` or `wikipedia` row exists for that field, so
they cannot contribute a name. **Any `state_parks`-canonical merge will surface
the GIS row's short name.** That affects far more than groups 66 and 70.

### Group 24 (Malakoff Diggins) — the richer text loses

Post-merge description was *"Travel 11-miles north on highway-49 toward
Downieville."*, attributed to `california_state_parks` `[literal]`.
`california_state_parks` is precedence 2 for description; `atlas_oddities` is 6.
So the canonical keeps its driving directions and the atlas row's substantive
text about the hydraulic mine **does not surface** — and its row is soft-retired,
so that text leaves the corpus. Not a bug; a consequence of precedence that is
worth seeing before running it.

### Groups 24 / 86 / 88 — the self-reference hazard is handled

Seeded the exact pre-condition: a `contained_in` edge from absorbed to canonical
**before** the merge. Result `[literal]`: edges **1 → 0**. No self-reference
(child = parent) survived, no edge still points at the absorbed row, no
duplicates. The v2–v4 work covers this class, now confirmed directly rather than
by assuming prior coverage generalises.

## 4. A THIRD failure class, found while checking 77/78

Phase 3 found two ways a group can be wrong (name-similarity miss,
centroid-distance miss). This is a third, and it lives **inside** a single
master_place rather than across group members: **a visitor `source_record` for
one park attached to a master_place named for a different park.**

Scanning all 257 members of all 123 groups for `similarity(mp.canonical_name,
source_record.name) < 0.45` returned **17 members**. Nine are benign
abbreviation artifacts (`Bodie SHP` ← "Bodie State Historic Park", `Hyrum` ←
"Hyrum State Park", and similar). **Eight name a materially different unit**
`[literal]`:

| group | bucket | mp name | attached source_record name |
|---|---|---|---|
| 55 | **106** | Ginkgo Petrified Forest | Wanapum Recreation Area |
| 74 | **106** | Silver Falls State Park | Smith Creek Village |
| 41 | **106** | Bothe-Napa Valley SP | Bale Grist Mill State Historic Park |
| 48 | **106** | McLaughlin Eastshore SP (SS) | Albany State Marine Reserve |
| 68 | **106** | Harstine Island | McMicken Island Marine State Park |
| 84 | **106** | Cave Rock Lake Tahoe-Nevada SP | Cave Rock |
| 77 | unmapped-9 | Mayer State Park | Historic Columbia River Highway - Rowena Crest Overlook |
| 78 | unmapped-9 | Fort Rock State Natural Area | Fort Rock Cave |

**Six of these are inside the 106 "already validated" groups, and in every case
it is the CANONICAL row that carries the foreign source_record** `[literal]`.

**I verified only 77 and 78 to description depth.** The other six are
`[unverified]` — several could be legitimately administratively-joined units
(Ginkgo/Wanapum, Bothe-Napa/Bale Grist Mill) rather than mis-links, and
distinguishing them needs the same per-case read that settled 6, 83, 77 and 78.
**Flagged, not resolved.** Note this class is invisible to the Phase 3 audit,
which compared member points to polygons and never looked inside a member.
